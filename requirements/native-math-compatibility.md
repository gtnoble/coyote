## 1. Scope and reference baseline

This user-approved SRS annex extends REQ-CORE-111/124 with the compatibility
target for the approved [port plan](../plan/native-math-parity-plan.md). The
implementation is partial and not yet qualified for the full approved target;
requirements approval does not establish parity or product acceptance. SRS-CORE
remains the authority for surrounding Markdown, sessions, image security, GTK
ownership, and Plain behavior.

The objective is the complete **core KaTeX 0.16.22 mathematical feature set**
within a reviewed finite domain, not merely the commands in the initial bug
report. Native runtime implementation remains Ada 2022 with Cairo/FreeType;
Node/KaTeX/browser tooling is development-only. Approved design and execution
authorize staged implementation. General TeX package loading, future upstream
versions, DOM serialization, and the JavaScript API are not implied by this
native target. Browser-sensitive features require the explicit
individual dispositions in §4; no blanket exception removes them from tracking.

Reference assets and original MIT notices are identified in
`share/coyote/math/PROVENANCE.md`. The pinned npm archive SHA-256 is
`e9e0d167db3175481cbadaff38e8d90b130f6a3ddb451a47e43c577fd511f365`.
The registry inventory is generated by `tools/inventory_katex.cjs` from the
unmodified distribution; its JSON records the bundle hash and source hashes.

## 2. Compatibility inventory and current gap assessment

The generated artifacts are
[the inventory summary](../plan/native-math-katex-0.16.22-inventory.md) and
[the detailed JSON](../plan/native-math-katex-0.16.22-inventory.json). Entries
are registration keys, often aliases or internal primitives, not independent
features or passing tests. Arbitrary user programs and combinations cannot be
exhaustively enumerated. Supporting source, Unicode, implicit syntax, settings,
and font inventories supplement registration counts.

The initial core registries contain 309 function names, 33 environments,
338 built-in macros, 2236 mode-specific symbol keys, and 14 settings. There
are 20 distinct font faces (60 files in three formats), versus nine faces in
the native model. All per-entry native coverage starts **unassessed**; no
compatibility percentage follows from these counts.

| Family | Current native evidence and gap | Required reconciliation |
|---|---|---|
| Lexing, syntax, macro scope | `Math_Syntax` scans a bounded subset directly; no user-macro namespace/expander (`math_syntax.ads:5–15`, `math_syntax.adb:157–184`) | Tokenization, expansion, namespaces, input normalization, errors and implicit syntax |
| Symbols/functions | Fixed `Symbol` table and `Parse_Atom`; many ordinary relations/functions absent (`math_syntax.adb:186–306,331–631`) | All registered names and mode restrictions; aliases and Unicode equivalents |
| Named operators | `lim`, `max`, `min` map to their first character (`math_syntax.adb:228–233`) | Complete word/glyph output and operator spacing/limits, not parse-only acceptance |
| Accents/annotations | Only hat/bar/vec in the accent branch (`math_syntax.adb:475–490`) | Full accent/decorations, overset/underset, extensible arrows/braces |
| Styles/fonts | Nine faces, limited style state; skew not consumed (native `Math_Model`, provenance) | All required faces, glyph metrics, style transitions and corrections |
| Arrays/tags | Ten named environments; no full column specifications (`math_syntax.adb:726–731`) | All core environments, rules, spacing, alignment, tags/numbering behavior |
| Delimiters/radicals | Natural sizes only; oversized structures rejected (`math_layout.adb:407–450,1033–1065`) | Extensible assemblies and path geometry |
| Output/presentation | Glyph/rule model, native text/image integration, source copy/fallback (`math_layout.ads`, `coyote_gui-math_element.adb`) | Color/path/semantic/interaction equivalents and policy-sensitive constructs |

Paths in this table are relative to `src/coyote_math/` unless otherwise named;
the GTK math element is in `src/coyote_gui/`. These are family-level code
observations, not per-entry differential results. P1 supplies measured baseline
classification and P2 supplies pilot effort data.

## 3. Approved requirements

Statements below are the approved normative target. Verification identifiers
refer to §6; they are planned tests, not existing passing cases.

**REQ-MATH-001 — Reference and accounting (I/T).** The compatibility inventory
shall identify the pinned reference version/configuration and every registered
function, environment, symbol/alias/mode, built-in macro, setting, implicit
syntax rule, and supporting Unicode/font/layout behavior. Every item shall have
an explicit status: unassessed, missing, partial, implemented-unqualified,
qualified, or approved deviation/not applicable. Evidence and review decisions
shall accompany status changes. No unresolved or failing item may be omitted
from final reconciliation or counted as passing.

**REQ-MATH-002 — Core parsing and expansion (T).** Within the accepted profile
and domain the engine shall match the reference's grouping, argument scanning,
mode restrictions, infix handling, optional arguments, comments/whitespace,
macro definitions/arguments/expansion, local/global assignments, and built-in
macro semantics, including parser-specific implicit commands. Unknown or
malformed input shall have the reference-equivalent success/error outcome.

**REQ-MATH-003 — State lifetime (T).** Independent engine requests and GUI
formulas shall use fresh macro state by default. An explicit caller-owned
shared context shall support reference-equivalent persistent definitions across
requests, including local scope restoration, global assignment, reset, and
error cleanup. State shall never leak across unrelated sessions or agents.
Re-rendering for zoom/replay shall not apply side effects a second time to an
already committed shared context. Persistence to disk is not required.

**REQ-MATH-004 — Symbols and Unicode (T/D).** The engine shall match the core
reference's symbol mappings, math/text modes, accents, Unicode script and
sub/superscript handling within the profile, including missing-glyph and
strictness behavior. This is not a promise of scripts or shaping beyond the
reference. Required fallback fonts/platform shaping shall be identified and
pinned in visual fixtures, not silently substituted during comparisons.

**REQ-MATH-005 — Layout and fonts (T/D).** The engine shall match reference
mathematical structure, atom spacing, glyph/font selection, style transitions,
script/limit positioning, metrics/corrections, and geometry to §5 tolerances.
All required core fonts and notices shall be packaged. Extensible delimiters,
radicals, arrows, accents, braces, and decorations shall not be limited to the
current four natural glyph sizes when larger in-domain reference output exists.

**REQ-MATH-006 — Constructs and environments (T/D).** All in-profile core
fractions, operators, annotations, styles, colors, dimensions, enclosures,
phantoms/overlaps, arrays, rules, alignment, tags and numbering shall have
reference-equivalent behavior. Accepting a command while dropping letters,
arguments, decorations, or semantic effects shall fail qualification.

**REQ-MATH-007 — Options (T/I).** The engine shall expose native equivalents
for the scalar/state options in §4. It shall distinguish parse-error handling,
strictness policy, and trust policy. JavaScript callback execution is not a
runtime feature; any native policy-hook equivalent needs a reviewed interface
and test cases. All unsupported option modes remain explicit deviations.

**REQ-MATH-008 — Diagnostics and fallback (T/D).** Engine results shall retain
the original source and distinguish valid output, warning, parse/strictness
error, policy refusal, resource limit, and font/layout failure. Source positions
shall have a documented UTF-8-byte/native to reference-position mapping; exact
exception classes, stack traces, and English error wording are not required.
Unknown-command/error fragments under `throwOnError=false` shall match the
reference's error presentation where representable. The GTK application may
instead show full source on fatal failure, an explicit application adaptation;
it shall not present a partial parse/layout as successful.

**REQ-MATH-009 — Untrusted input (T/I).** Formula processing shall perform no
network access, file/package inclusion, process execution, or arbitrary HTML/
CSS execution. The default policy shall be reference `trust=false`.
Trust-gated constructs shall be parsed and represented/refused as the reference
does under that policy, not misreported as unknown commands. Warnings shall
not silently authorize trusted effects. Policy-sensitive constructs and any
approved native equivalents shall follow §4.

**REQ-MATH-010 — Resource safety (T/A).** The engine shall enforce the reviewed
source, token/expansion, node/depth, array, output-command, dimension, memory,
and work budgets before unsafe allocation/processing. Exceeding a budget shall
produce bounded cleanup and visible source fallback rather than a crash or
unbounded GTK stall. Limits and limit-induced differences shall be reported;
limits shall not excuse semantic discrepancies for in-domain cases.

**REQ-MATH-011 — Native integration (T/D).** Existing inline/display delimiters,
Markdown code protection, original-source copying, selection, zoom, theme
foreground, baselines, replay, and surrounding local-image policy shall be
preserved. GTK operations shall remain on the GTK main task. Formula processing
shall not introduce a JavaScript/browser/reference-engine production dependency.
Plain presentation and stored session source shall remain compatible.

**REQ-MATH-012 — Semantics and accessibility (T/D/I).** Native output shall
expose formula source plus structured mathematical content adequate for
assistive-technology navigation and distinguish applicable links/annotations
from ordinary glyphs. Copying shall recover exact delimited input. Final
qualification shall include human review with named desktop/assistive tools;
bitmap similarity alone shall not satisfy this requirement.

**REQ-MATH-013 — Differential evidence (T/I).** The qualification corpus shall
cover every in-profile inventory item and relevant mode/option, representative
interactions/nesting, valid/invalid/boundary cases, macro-state sequences, and
the originally reported heat-balance equation. It shall compare reference and
native outcomes, diagnostics categories, geometry and visual output as in §5.
Reference snapshots shall record upstream version, source/configuration hashes,
fonts, platform, and tool versions. Test counts shall not be called a language
coverage percentage.

**REQ-MATH-014 — Regression and robustness (T/I).** Each increment shall pass
its focused tests and agreed regression gates. Final qualification shall include
root/test development builds, full registered suite, standalone ownership/
resource checks, seeded malformed-input/expansion fuzzing, cancellation/failure
paths, and GUI integration. Known failures and manual/deferred tests shall be
reported, not treated as passes.

**REQ-MATH-015 — Maintainability (I/T).** Reference-derived code/data shall keep
provenance and required notices. Generation and qualification shall be
repeatable from documented pinned inputs without npm package installation or
runtime reference-engine use. Upstream updates shall be separately reviewed
changes with inventory diffs, regenerated evidence, and regression assessment.

## 4. Option and policy dispositions

Reference defaults below come from `new Settings({})`, not CLI defaults.
Default and exercised profile values shall be recorded in each test case.

| Setting | Reference default | Approved native disposition |
|---|---|---|
| displayMode | false | Both false/true; GUI determined by source delimiters |
| output | htmlAndMathml | Native drawing plus semantics; no markup serialization; markup modes tracked in D01–D03 below |
| leqno | false | Match both tag placements |
| fleqn | false | Match both display alignment modes |
| throwOnError | true | Match engine outcome/error-fragment modes; GTK source fallback adaptation in REQ-MATH-008 |
| errorColor | #cc0000 | Match explicit error colors; GTK fatal-source fallback follows normal readable theme |
| macros | empty object | Initial definitions and explicit shared native context; no JavaScript function bodies |
| minRuleThickness | 0 | Match finite nonnegative values in domain |
| colorIsTextColor | false | Match both historical/color declaration behaviors |
| strict | warn | Match warn/ignore/error and boolean policies; native diagnostics rather than console output; callback mode tracked in D11 below |
| trust | false | Default mandatory untrusted profile; trusted/hook dispositions below |
| maxSize | Infinity | Reference default recorded; primary qualification uses 100 em cap, an approved safety-profile difference |
| maxExpand | 1000 | Match finite budgets through approved maximum 10000; no unbounded expansion promise |
| globalGroup | false | Match both settings in an explicit context; GUI default false |

Three profiles are approved: default untrusted inline/display with strict=warn;
strictness variants with ignore/error/boolean values; and caller-configured
finite scalar/state options. They share §5 budgets. Baseline reference
comparisons use `throwOnError=true`, `maxSize=100`, `maxExpand=1000`, `trust=false`;
error-fragment tests use false explicitly. Unbounded settings and JavaScript
callback bodies are not claimed equivalent.

| Browser/policy-sensitive feature | Approved disposition |
|---|---|
| `\href`, `\url` | Match untrusted refusal/visible command behavior; trusted link modes excluded by D04–D05 below |
| `\includegraphics` | Match untrusted refusal and argument validation; no formula-triggered file/network loads; trusted image mode excluded by D06 below |
| `\htmlClass`, `\htmlId`, `\htmlStyle`, `\htmlData` | Match untrusted/strictness behavior; arbitrary DOM/CSS side effects have no native equivalent and are approved interface deviations, not silently ignored inputs |
| `\html@mathml` and built-in wrappers | Use HTML branch for visual comparison and retain semantic branch for accessibility; native semantics need design review; markup serialization excluded |
| Trust/strictness callback options and function-valued caller macros | No JavaScript execution; callable modes excluded by D11–D12 below; later native hooks are not assumed equivalent |
| Optional contrib extensions (including mhchem and auto-render) | Separately inventoried; approved outside initial core target, not counted as implemented; existing native Markdown extraction is still qualified independently |

User approval authorizes **pinned core mathematical parity within the stated
native/untrusted profile**, not unrestricted trusted browser/API parity. The
long-term inventory retains excluded behavior as excluded, never qualified.
Expanding these boundaries requires a reviewed requirements change.

D01–D15 below were approved with this requirements annex. Their acceptance
rule is to preserve accounting and verify no excluded side effect; they are
outside the parity qualification denominator and must be reported separately.
Untrusted input handling for the same commands remains inside the profile.

| ID | Observable reference behavior outside profile | Approved native disposition |
|---|---|---|
| D01 | `output=html` serializes visual HTML/CSS/SVG | Native visual output; no byte-identical markup export |
| D02 | `output=mathml` serializes semantic MathML | Native semantic/accessibility channel; no XML export |
| D03 | `output=htmlAndMathml` serializes both markup trees | Native visual plus semantic channels, not DOM/API compatibility |
| D04 | Trusted `\href` creates an active anchor around its body | No active trusted formula links in initial profile |
| D05 | Trusted `\url` creates an active URL anchor | No active trusted formula links in initial profile |
| D06 | Trusted `\includegraphics` emits an image resource | No formula-triggered image loads; surrounding Markdown policy unchanged |
| D07 | Trusted `\htmlClass` attaches DOM classes | No arbitrary DOM class attachment |
| D08 | Trusted `\htmlId` attaches a DOM identifier | No arbitrary DOM identifier attachment |
| D09 | Trusted `\htmlStyle` attaches CSS styling | No arbitrary CSS execution |
| D10 | Trusted `\htmlData` attaches data attributes | No arbitrary DOM data attributes |
| D11 | Function-valued `trust`/`strict` invoke caller JavaScript | Callable modes excluded; scalar policies still mandatory |
| D12 | Function-valued caller macros invoke JavaScript expansion code | Callable macros excluded; textual/token definitions still mandatory |
| D13 | Infinite expansion or unbounded sizing may exceed native limits | Finite domain only; report limit differences separately |
| D14 | Optional contrib modules add chemistry/auto-render and other features | Core target only; retain each contrib file as excluded extension |
| D15 | JavaScript render/DOM/parse and extension APIs | Native interfaces, no JavaScript API compatibility |

All core entries not covered by an approved deviation remain required.
`\html@mathml` is not excluded: compare its visual branch to the HTML reference
and retain its semantic branch for native accessibility. User macro scoping and
core `\def`/`\gdef` behavior remain required.

## 5. Approved finite domain and provisional visual thresholds

Resource/performance budgets below are approved targets, **not measurements
or achieved results**. Geometry/visual comparison criteria retain the stated
calibration and test-readiness gates before acceptance use. Reduced limits or
relaxed tolerances require a recorded requirements change.

| Limit | Approved target | Current native starting point |
|---|---|---|
| Source UTF-8 bytes per expression | 65536 | 4096 |
| Emitted lexical/expanded tokens per request | 131072 | No separate expander/token budget |
| Macro expansion count | Default 1000; configurable up to 10000 | No user expander |
| Syntax nodes / argument depth | 32768 / 128 | 2048 / 32 |
| Array rows / columns | 64 / 64, still bounded by node/output budgets | 32 / 32 |
| Layout depth / draw commands | 256 / 131072 | 64 / 16384 |
| Absolute calculated dimensions | 16384 em; user sizing capped at 100 em | 16384 em layout bound |
| Final inline / display surface including padding | 2000×512 / 8192×4096 pixels | Existing geometry checks plus four-pixel padding |
| Native math job additional memory | At most 256 MiB, including transient output; fonts/preexisting GUI baseline reported separately | Not measured |
| Retained raster-cache growth | At most 64 MiB total per process; source/session retention measured separately | Not qualified |
| Processing latency on qualification workstation | Warm fixed representative corpus p95 ≤50 ms; bounded jobs terminate/reject within 250 ms; no synchronous GTK math work slice over 50 ms | Not measured |

The limits form a conjunction: an expression must meet every bound. Reference
errors remain errors; within-domain successful reference cases must not be
rejected merely for a missing native feature. Over-limit native rejection is
not semantic parity with unbounded reference input. Source retention remains
subject to the application's session/message limits and is not included in the
math-workspace budget. Display rendering may use native drawing rather than
allocate a maximum-size surface; retained rasters must respect the cache bound.
For accounting use ARGB32 actual Cairo stride × height: a maximum 8192×4096
surface alone occupies 128 MiB before intermediate buffers. The 256 MiB job cap
includes owned syntax/tokens/layout, new surfaces and intermediate buffers;
cached copies count during the job too, then against the 64 MiB process cache.
A surface larger than the cache must not be retained there. Report accounted
allocations and isolated-process peak RSS above a fixed warmed baseline
separately. Shared font caches and session source retention are reported
separately. Surface bounds do not require every output to be rasterized.

Comparison targets (calibration/readiness conditions retained):

- Identical accept/error/policy outcome and equivalent mathematical structure;
  aliases normalize only through reviewed rules. Compare diagnostic categories
  and positions, not engine-specific exception text.
- For geometry, use identical bundled faces and em size; absolute differences
  in dimensions, glyph origins, baselines, rules and paths must be ≤0.01 em.
  P1 must export reference layout-tree boxes, glyph origins and SVG geometry
  normalized to a common baseline/em scale, and corresponding native commands.
  Compare matched semantic constructs, not arbitrary DOM indices. If an
  internal quantity is not exportable, measure browser glyph/box bounds with
  declared uncertainty. Unresolved comparisons remain failures or pending
  test-readiness decisions, not omitted assertions.
- Visual fixtures: pinned browser/device scale, font files and viewport;
  transparent backgrounds, matched explicit colors, aligned baseline without
  free rescaling. At 24 px/em, construct each foreground mask using alpha ≥0.1
  after
  transparent-background rendering. For each foreground pixel compute Euclidean
  distance in output pixels to the nearest foreground pixel in the other mask.
  Require distance ≤1 pixel for at least 99% of pixels in each direction, not
  a combined denominator. One empty and one nonempty mask fails; two empty
  masks pass only for semantically empty reference output. Also require the
  same reviewed semantic component count, ≤0.01 em component bounds, and RGBA
  channel differences ≤2/255 at interior pixels (>1 pixel from mask edge).
  Edge-only tiny components receive separate geometry/color checks; absence of
  interior pixels is not an automatic color pass. This prevents dropped small
  accents hiding in a global pixel allowance. P1 must calibrate these draft
  criteria on frozen fixtures and deliberate missing/extra/shifted/wrong-color
  controls before test-readiness approval. They are not accepted thresholds.
- Timing: record workstation/OS/compiler/browser and warm/cold conditions;
  p95 uses at least 200 specified representative cases, 10 timed iterations
  after one warm-up, including nested/array/macro cases. Measure extreme and
  hostile inputs separately for hard budgets; do not average stalls away.
  Name the workstation and frozen environment at test readiness. Time jobs
  from submission to completion/rejection with a monotonic clock, including
  queue wait and cancellation cleanup; instrument GTK work slices independently.
  A watchdog test detects >250 ms unfinished jobs and verifies cancellation/
  cleanup separately; a watchdog kill is not compliant job behavior. Infeasible
  thresholds return to requirements review before any relaxation.
- Robustness: require at least 10000 seeded generated/adversarial cases per
  final qualification run, plus deterministic limit/ownership/failure tests.
  Fuzz success alone is not proof of all-input safety or complete equivalence.

No new hardware procurement, deployment sites, or personnel/training obligations
are proposed. Corpus storage and acceptance-run time will be measured in P1;
calendar/cost estimates follow the P2 pilot. Cancellation mechanism, workspace
accounting, policy interfaces, and rendering partitioning are design decisions
still subject to review, not preselected implementations.

## 7. Open decisions and evaluation

The user approved the version/profile, complete-core accounting, native/API
and optional-extension boundaries, D01–D15, state behavior, resource targets and
verification families on 2026-10-24. These approved requirements remain
unchanged. Native design and project execution are approved; implementation is
partial, with P1 readiness and final qualification still open. The approved
scope must not be narrowed by implementation gaps. Geometry/visual calibration
and independent acceptance remain pending.

performance feasibility and final test readiness remain pending. P1 baseline and
browser tooling exist but full field matching/readiness are incomplete; P2 pilot
works; P3/P4 and P5 remain partial; P6 acceptance is open. The final report is
planned at `plan/native-math-parity-test-report.md`; final qualification pending.

requirements have source and verification links; unmeasured budgets and scope
deviations are labeled. Current native coverage is not fabricated. Limit and
visual thresholds require feasibility calibration and review; this draft does
not claim them achieved. Read-only review found no remaining blocker to presenting this proposal
