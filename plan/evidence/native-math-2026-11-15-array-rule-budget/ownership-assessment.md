# Ownership assessment: extending Parse accounting to retained results

**Purpose.** Read-only architecture assessment following the verified array-rule construction increment (§11.16). This identifies the next ownership/accounting decision needed for a defensible whole-job 256 MiB account. It proposes no implementation and does not claim parity, resource qualification, or acceptance.

## Decision in brief

**Do not extend the current borrowed Parse reservation into the returned `Document` under the existing API/lifetime contract.** That would make its account pointer outlive its account, or require charging a worker-local ledger after the worker's stack frame ends. The `Document` is a nonlimited, assignable value returned by `Parse`; it is stored in `Job_Result`, copied out by `Parse_Document`, and copied into GUI state. Its nested vectors and strings are owned by each value, but current Parse charges end when parser locals finalize.

The architectural gate is narrower than “all coding is blocked”: before claiming whole-job memory accounting, approve how ownership and budget lifetime are represented across `Document` and subsequent retained products, including copies and overlaps. Independent scoped improvements, instrumentation, and tests can continue, but extending charge lifetime safely is not just a parser-local change.

## Verified ownership and lifetime facts

### Parse and Document

`Math_Syntax.Document` is private in the visible API and an ordinary nonlimited record in the private view (`src/coyote_math/math_syntax.ads:114-168`). It owns `Text`, `Message`, a node vector and diagnostic vector. Nodes themselves carry unbounded strings and `Array_Rules` vectors (`math_syntax.ads:43-97`). There is no controlled finalizer or limited ownership in `Document`.

All four public `Parse` overloads return `Document` by value (`math_syntax.ads:118-132`). Their `Work` and `Memory` arguments are documented as borrowed for the call only. The current contract explicitly says returned/copy lifetimes are not charged and parser reservations release after parser locals finalize (`math_syntax.ads:133-144`). In the implementation, vectors are moved from parser state into the result, but this only avoids a construction-time vector copy; it does not alter later assignment/copy semantics (`math_syntax.adb:3450-3463`).

The API permits ordinary assignment and repeated replacement. Tests assign Parse returns into existing Documents (`test/src/coyote_math_tests.adb:174,224,281-291`). `Element` returns a Node value and `Diagnostic_At` a Diagnostic value (`math_syntax.ads:145-154`), adding further copy paths for owned payloads.

### Worker and ledger

`Coyote_Math_Jobs.Job_Result` is limited, but its `Parsed`, `Geometry`, and `Meaning` components are ordinary value types (`src/coyote_math/coyote_math_jobs.ads:101-115`). Worker task `Run` declares an aliased `Math_Memory_Budget.Budget` as a local object (`coyote_math_jobs.adb:413-...` worker declarations) and passes `Memory'Unchecked_Access` to Parse (`487-489`). It reads the peak and resets it after Parse; subsequent semantics/layout/raster phases run with Parse returned and its reservations finalized (`489-510,539-548`). The `Job_Result` may persist after the task's local `Memory` has gone out of scope.

`Math_Memory_Budget.Reservation` is limited controlled, but it stores a `Budget_Access`; its specification explicitly requires the Account to outlive every referring reservation and assigns this lifetime responsibility to callers (`src/coyote_math/math_memory_budget.ads:1-16,38-53`). Finalization dereferences that account to uncharge (`math_memory_budget.adb:83-87`). Thus a Reservation attached to a Document but referring to the current worker-local Budget would be dangling when the worker scope ends. Keeping the Document only inside limited `Job_Result` does not extend the worker's stack lifetime.

The current memory budget type has 256 MiB capacity per Budget instance (`math_memory_budget.ads:20`). A stack-local instance per worker is not a shared process-wide concurrent 256 MiB cap. The separate raster retained-output ledger is process-shared and 64 MiB (`math_raster_budget.ads`); it covers retained raster leases, not AST/semantics/layout ownership. These are distinct accounting scopes.

### Consumers, copies, and later products

Production Parse storage sites include `Math_Engine` assigning the return into `Output.Parsed` (`src/coyote_math/math_engine.adb:84-86`; field at `math_engine.ads:50-56`), the worker assigning into `R.Parsed` (`coyote_math_jobs.adb:487-489`), and inline rendering's local parsed value (`coyote_gui/coyote_gui-math_element.adb:907-912`). `Coyote_Math_Jobs.Parse_Document` returns `Item.Parsed` by value (`coyote_math_jobs.ads:70-72`, `.adb:808-813`); display math assigns that return into the GUI element's own `Parsed` field (`coyote_gui/coyote_gui-math_element.adb:599-601`; field in `.ads:100-112`). That retained GUI Document can outlive and be independent of the job result.

`Math_Layout.Build` accepts a Document by value (default `in`) and returns a separate ordinary Box by value (`src/coyote_math/math_layout.ads:81-94`). Box owns a command vector; commands can own path vectors and strings (`math_layout.ads:34-77`). Worker assignment stores the built Box in `R.Geometry` (`coyote_math_jobs.adb:539-548`), and GUI's `Layout` accessor returns it by value before assignment into element state. Semantics projection similarly produces a separate retained document (`math_semantics.ads:86-88`; worker `coyote_math_jobs.adb:505-510`).

Painting accepts Box by value; painter code copies commands locally, including payload-bearing command data (`src/coyote_math/math_painter.ads:43-50`, `.adb:467-474,665-670`). Raster output is another owned value. Worker rendering uses `Render_Into` into `R.Pixels`, while retained raster output has its own lease. During GUI adoption, worker result pixels and GUI Cairo surface/Pixbuf coexist; result disposal follows row-batched copy completion (`coyote_gui/coyote_gui-math_element.adb:463-544,631-646`; rich-text inline adoption at `coyote_gui/coyote_gui-rich_text.adb:482-528`). This overlap matters to the 256 MiB transient-output rule even though the 64 MiB retained-raster ledger exists.

## Concrete dangling-budget failure mode

A tempting change is to place a `Math_Memory_Budget.Reservation` in `Document` and retain the current `Memory` account pointer. In the worker, that pointer identifies the local `Memory` object in the worker's nested job block. Parse returns, `R.Parsed` persists, and eventually the local Budget finalizes/leaves scope while `R.Parsed` remains reachable through the published result (and potentially a copied GUI Document). The Document reservation's finalizer would later invoke `Uncharge` through a dangling access value. This is invalid lifetime management, not merely undercounting. Making `Job_Result` limited does not prevent `Parse_Document` from copying the underlying Document into longer-lived GUI state.

Changing the Budget from local to a worker field alone is also insufficient: one worker field can be reused for another job while earlier results survive, and concurrent workers would still have separate 256 MiB caps. A process-shared account would fix account lifetime only if its storage is guaranteed to outlive every reservation, but it does not by itself provide sound Document copy accounting, ownership transfer semantics, or accounting for overlapping copied payloads.

## Is a safe extension possible without new ownership architecture?

**No, not with the current public API and stated lifetime contract.** A safe extension requires at minimum an explicit policy for account lifetime, result/document lifetime, copying, and charges across phases. That is an ownership/accounting architecture decision even if its first implementation is small. The present API gives Parse only a borrowed account and gives callers an unrestricted copyable value; it does not provide a transfer/clone/retain/release protocol.

Possible designs for review:

1. **Keep Parse accounting transient; add explicit retained-result accounting at the owning job boundary.** Parse charges construction overlap and releases on return as now. A job-lifetime owner accounts for retained AST/semantics/layout and tracked copies/overlaps through result disposal; GUI adoption and copies need explicit treatment. A process-wide or otherwise correctly scoped account must outlive leases. This preserves the ordinary Document API but requires defined size/copy accounting and likely explicit job/result lifecycle integration. It is not enough merely to charge one vector capacity after Parse.
2. **Make Document an owned/limited resource with controlled finalization and explicit clone/transfer APIs.** Each ownership instance can hold a lease; move/transfer and deep clone can be charged deliberately. This is a significant source/API migration: assignments and by-value `Parse_Document` consumers need replacement with move, borrow, or clone operations; aggregate/result fields and tests change. The account must still be stable and outlive all Documents, including GUI copies. Controlled finalization alone does not intercept ordinary deep-copy semantics safely; a copyable controlled type needs a correct `Adjust`/clone-and-charge design and clear exception behavior, while making it limited removes implicit copying but requires all current callers to change.
3. **Use immutable shared backing storage with reference-counted ownership.** Copies become handles to one accounted AST allocation, charged once until final release, while explicitly cloned data is separately charged. This changes representation and adds synchronized lifetime/refcount and failure semantics; nested strings/vectors must actually share backing storage for the claimed accounting. It offers a coherent way to make by-value handle copies cheap but is the largest architectural change.
4. **Constrain accounting to a pipeline lifetime and prohibit escaped copies.** Keep Document nonlimited but make Parse/consumers callback- or owner-scoped so all products are accounted until a defined completion point, and avoid returning independent copies. This would require changing `Parse_Document` and GUI retention contracts; it cannot be achieved by extending the current borrowed reservation alone.

The design review should choose and bound one of these models (or reject retained Document charging as out of scope with a requirements disposition). At minimum decide: account scope (per job versus process concurrency), when each charge begins/ends, treatment of deep copies and vector/string capacity, whether cache/GUI-retained values remain in the job budget or transition to another ledger, and how cancellation/error/clone failure releases charges. Do not infer allocator/RSS precision from Ada container capacities; §11.16 explicitly notes GNAT-specific requested-capacity behavior and excludes allocator overhead.

## Next blocker versus other work

This is the **proposed architectural gate for asserting whole-job 256 MiB accounting**, because REQ-MATH-010's approved target includes owned syntax/tokens/layout, new surfaces/intermediate buffers, and cached copies while the job runs; §11.16 expressly excludes returned/cache lifetimes and several pipeline allocations. It is not a blocker to all further scoped development. Parser phase accounting, independent measurements, copy-site inventories, bounded work checks, or separately scoped subsystem improvements can proceed without claiming the full-job cap. But no result from those scopes closes whole-job accounting until the ownership model and concurrent account scope are decided and implemented/verified.

REQ-MATH-010 also requires isolated-process peak RSS above a fixed warmed baseline to be reported separately from accounted allocations (`requirements/native-math-compatibility.md:149-154,270-298`). Even a complete logical ownership ledger would not itself prove the RSS target. Hard 250 ms completion, GTK 50 ms slice, warm p95, allocator/native/font behavior, full parity, lifecycle, and human acceptance remain separate open gates; this note closes none of them. §11.16 remains the controlling evidence for the array-rule increment and states PCR-125 OPEN / feature NOT COMPLETE.

## Approval requested

Request an **approval-required design proposal/review** before modifying Document ownership or exposing a retained Parse budget. The review should decide among the alternatives above, specify charge and release semantics for copies and result-to-GUI retention, and define process-wide versus per-job concurrency enforcement. Until approved, retain the current borrowed Parse-budget contract and describe its measured scope accurately. This is a recommendation for the next accounting design decision, not a claim that all project coding is blocked or that any parity/acceptance criterion has been met.
